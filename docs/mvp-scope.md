## 1. What this is

Vigil is an explainable airspace-triage workstation for the Philadelphia-area airspace (PHL). It fuses two layers into one picture — real, publicly broadcast ADS-B traffic (the cooperative aircraft) and simulated small-UAS tracks (the injects) — scores every track against a protected site using transparent logic, and presents a ranked queue so a watch officer always knows which track deserves attention first, and exactly why.

The project has two jobs, in this order:

1. **Learning vehicle.** Every change ships through the full modern path — issue, branch, PR, AI code review, CI, engineering review, iteration, merge — so the vocabulary and mechanics of end-to-end shipping become muscle memory.
2. **Portfolio artifact.** A public repo with a clean PR history demonstrating, to a Director-level panel, a PM who ships with AI agents in a hot, industry-relevant domain (counter-UAS / airspace security).

## 2. Hard guardrails (non-negotiable)

- **Public or synthetic data only.** The real layer is ADS-B — broadcast in the clear by aircraft and freely rebroadcast by community aggregators. The threat layer is 100% generated. Nothing observed, recorded, or derived from any work system ever enters this repo.
- **Real aircraft are never the threat.** By design, any track sourced from ADS-B is treated as cooperative and receives low baseline priority. Only synthetic injects can score as threats. This is both an ethics rule and a product truth (broadcasting your position is the defining cooperative act). Vigil also never singles out specific individuals' aircraft — no VIP or celebrity tracking; real tracks receive special attention only for assistance signals they broadcast themselves (see Phase 2).
- **Public first principles only.** Design draws exclusively on open literature: CPA/TCPA geometry, published counter-UAS concepts, FAA Remote ID as public context. No Camgian or Reactor requirements, terminology, code, or documents — if a design question can only be answered from work knowledge, pick a different design.
- **Not an operational system.** README states plainly: educational demonstration, not for operational use, no claims about real-world threat assessment.
- **No simulated engagement.** Vigil never models jamming, takeover, or kinetic defeat. Its act step ends at assessment and notification — which is both the ethics posture and the watch floor's actual job (see §7.1).
- **Public repo from day one.** Openness is the enforcement mechanism.

## 3. User and job

**The watch officer for PHL-area airspace security** (the *job* is inspired by a real conference conversation about airport-area safety in another region; the person and their systems stay out of this project, and the geography moved home). They monitor a workstation covering the region. Job statement: *"When something is flying near a protected site that shouldn't be, I need to know first, with a reason I can act on and defend."* The interesting traffic is exactly what ADS-B doesn't show — so Vigil's premise is: render the cooperative picture as calm background, and make the non-cooperative injects impossible to miss.

## 4. Product principles

1. **Explainability over cleverness.** Every score decomposes into visible factors — including, eventually, the learned ones. A ranked list nobody can interrogate is a liability.
2. **The queue is the product; the map is context.** Screen real estate serves the ranked list first.
3. **Plain language, intuitive at a glance.** No military symbology standard. Identity states in English (Cooperative / Non-cooperative / Unknown), calm colors for calm traffic, alarm colors earned only by score. A smart civilian should read the screen cold.
4. **Doctrine is configuration, not code.** Weights are data. MVP hardcodes defaults; the architecture assumes they change — first by slider, later by learning.

## 5. The picture

The AO is pure configuration — center point, capture bounding box, protected sites. PHL by default; relocating Vigil to any other region is a config change, not a rewrite.

### 5.1 Real layer — recorded ADS-B, replayed

- **MVP uses a recorded fixture, not a live feed:** a capture script pulls ~15–30 minutes of real PHL-area traffic once from a public aggregator, saved as JSON in the repo, replayed on a clock. This keeps tests deterministic, demos reproducible, and the MVP free of rate limits, CORS, and outage risk. Going live is Phase 2, where it belongs — behind the backend.
- **Two recordings, selectable** (#84, ruled). `vigil-phl-001` is the small-hours picture the golden and every pinned test run on; `vigil-phl-002` is an evening arrivals bank inside operating hours — the same doctrine watched against a different sky and hour. A registry in `src/config/recordings.ts` holds each recording’s id, file, and clock start; `?recording=<id>` selects one, the default without it is 001, and a name that matches no recording is a load error that says so, never a silent fallback. **A recording carries its own clock start:** 001’s is configured at 02:30, for §13; 002’s is `'captured'` — its `capturedAt` read in the AO’s time zone (`timeZone` in `src/config/ao.ts`) at load, so the file’s shape is unchanged and an evening bank opens in the evening. The off-hours factor, the strip’s sim clock, and the record’s sim-time stamps all read it. Selection is the query parameter or the registry’s default; there is no picker on screen.
- **Replayed between the samples, not snapped to them** (06a, ruled on #6). The recording samples every fifteen seconds and the replay clock ticks every second, so each aircraft is bracketed by its own two samples either side of the clock and read linearly between them — position, altitude, ground speed, vertical rate, and the heading the short way round the compass. A track is absent before its first sample, never interpolated into existence; a hole inside its span no wider than the coast window is bridged the same way while its `seen` ages honestly from the last real message. After its last sample it holds there while `seen` accrues and leaves the picture once that passes the **coast window** — 90 s in `src/config/replay.ts`, one sample past the 60 s the aggregator itself coasts a track for. Staleness is a data-quality signal, not threat evidence: it is handled by the coast, the drawer's Seen row, and the identity dwell, and it is not a factor.
- **Source:** adsb.lol (free, open-data, unfiltered API) for the capture; OpenSky Network (free for research/personal use, registered account) as backup.
- **Capture etiquette.** The aggregators are free services running on donated receivers, and a capture that abuses one is a capture that stops working: the script floors its polling interval at 10 seconds — after a backoff too, skipping the slots the delay ran past instead of firing the backlog back to back, which is the moment abuse is least affordable — honors `Retry-After` verbatim, and abandons the run on the second 429 rather than grinding through a rate limit into a block. A backoff that would end past the run's last slot is not slept through: the run stops in the same second, and the frames it never reached count as missing like any others (#41). A recording is written only within its **gap budget** — a tenth of its frames, with a floor under the rate at the cost of the one 429 the etiquette tolerates, the failed request plus the slots a 60 s backoff runs past (five at 15 s) — so a short capture survives the event the rules permit while a long one keeps the rate (#36 [3]). Missing is counted as missing, not merely failed: a slot skipped to hold the floor after a backoff leaves the same hole as a frame that failed outright and spends the budget the same way. Arguments that do not describe at least one whole frame are refused before any request goes out. The window has a floor and no ceiling: its length is the operator's to choose (#44). An infinite window was dangerous because it defeated guards — it made the frame count pass a check written to stop it; a large finite one defeats nothing, and every check behaves the same all the way through a long capture.
- Fields normalized into the common track model: ICAO hex, callsign, position, altitude, ground speed, heading, vertical rate, last-seen.
- **Enrichment fields are display-only.** The recording also keeps the broadcast emitter category and the aggregator's registry lookups — type code, type description, registration. They are shown labelled by provenance (observed vs. lookup) and never scored: nothing in the scoring path reads them, and a test pins it. **Runtime third-party calls are permitted only for display enrichment that fails soft; nothing in the scoring path reads the network.** **Vigil displays what is broadcast or what a public type registry says about the airframe; it never resolves a tail number to a person** — the feed's registered owner/operator field is deliberately not captured, and an airline operator, if ever wanted, comes from a callsign-prefix table, which can only name a company.

### 5.2 Synthetic layer — the injects

- 5–8 simulated small-UAS tracks per scenario (the floor is the behavior count, so every behavior appears in every scenario — the generator refuses a lower floor): low altitude, slow, launched from synthetic points around the region. Launch points are a bearing and a range from the AO center, so relocating the AO relocates them, and all of them sit outside the protected-site ring — an inject has to fly to get inside. Seedable and deterministic: same seed → identical picture, pinned by a committed golden fixture rather than by a snapshot. One seed under every recording (ruled on #84): 002 plays the same injects as 001, so the contrast between recordings is the sky and the hour, never the drones.
- **A scenario is a function of seed and config alone; the timeline samples it and never reshapes it.** Recapturing the ADS-B layer at a different length or cadence adds or removes frames of the same injects — it does not deal a different scenario. The timeline is the recording's own frame times, not a count and an interval: the generator is asked at each instant the recording actually has, so a hole in the recording is a hole in both layers rather than a stale offset, and the plan — the dropout chain included — is sized from the recording's span, so a gappy recording and a contiguous one of the same length deal the same injects (#39).
- Each inject carries a **Remote ID status**, in three states, and the picture reports the *observed* identity rather than the label:
  - **Broadcasting** → **Cooperative.** A legitimate hobbyist or Part 107 operation, identifying itself. Low priority.
  - **Intermittent** → **Cooperative on the frames the broadcast is heard, Unknown on the frames it is not.** The dropout is real, not a label: the broadcast genuinely comes and goes across frames, in runs rather than one frame at a time, and the ident disappears with it. The resulting per-frame flicker is by design at the data layer — smoothing it (identity dwell, or hysteresis on the last confirmed ident) is a scoring concern and belongs to PR 04.
  - **Silent** → **Non-cooperative.** Nothing is broadcast at all. The interesting case.
- The `remoteId` field is ground truth about the airframe; identity is what the picture can actually tell. Scoring reads the observed history, never the label — see PR 04.
- Each inject also carries a **Remote ID UA type** (ASTM F3411's public list, reduced to multirotor, aeroplane, and hybrid lift), drawn from a per-inject derived stream so that lengthening the recording or re-weighting the draw moves nothing else in the scenario. It is observed only on the frames the broadcast is heard — a silent inject never shows one, and the picture classes it from its motion instead: *small UAS (kinematic class)*, labelled as such.
- This mirrors the real triage problem: the question is never "is it a drone," it's "is it identifying itself."
- Scenario scripts give injects *behaviors*: transit, loiter, orbit a point, lawnmower/grid sweep, approach-and-retreat. Behaviors are what the pattern features in §6 exist to catch.
- **Protected sites:** the configured set is the PHL airfield, a point plus radius — the default and the golden. From 08a (ruled on #86) the operator edits the set during a session on the Sites surface — add by a map click, move, resize, rename, re-tier, remove — circles only, as session state: a reload returns to config, and every recording and every pinned test plays against the config set. A site carries a **tier**: 1 is protected in full; 2 scales its closing and proximity value by a configured multiplier (0.5 in `src/config/scoring.ts`) before the worst case across sites is taken, so presence inside a tier-2 ring reads caution and a pattern inside it warning — attend, not act, until it behaves. **Stretch:** schedules — the South Philadelphia sports complex (three major venues in one square mile) becomes protected on event nights, which turns time-of-day from a number into a story; a per-site active window is filed as a follow-up at 08a's open (#91).
- **Friendly launch areas** (08b, ruled on #86): the inverse fence. A department's own drone unit launches from a known spot, and without a declared friendly area its own Remote ID tracks top the queue on day one. A friendly launch area is a circle the operator draws; a track whose **observed first-seen position** lies inside one *and* which is **heard on Remote ID** — now, or within the identity dwell, the same window the Identity factor holds a heard ident for — is capped like a cooperative aircraft, at `friendlyCap` in `src/config/scoring.ts` (its own value, defaulting to the ceiling's 30). A silent track first seen inside the area gets no cap: the origin is observed, the identity is not. The condition reads the picture — the recording's first sample, the inject's first frame — never the generator's launch points, so the cap is keyed on what is observed, never on a label. No default areas in config; the set is the session's.

## 6. Scoring engine v1 — transparent factors

A pure TypeScript module producing a 0–100 composite with the per-factor breakdown retained for display. All factors below are deterministic and hand-weighted in v1 — the learned layer comes in Phase 3 (§8).

| Factor | UI label | Intent (doubles as hover text) | Default weight |
|---|---|---|---|
| Cooperativity | Identity | Silence carries the burden of proof — a spectrum: ADS-B aircraft near-floor, Remote ID drones low, silent tracks high | 25% |
| Closing geometry | Closing | CPA distance and time-to-CPA relative to the protected site | 20% |
| Proximity | Proximity | Current range to the protected site, decaying with distance — the curve spikes inside the protection ring, which subsumes "airspace violation" for MVP | 15% |
| Pattern of life | Pattern of life | Loiter dwell, orbit detection (persistent turn rate), area revisit — the reason tag names the specific behavior; the row carries the evidence | 15% |
| Kinematic profile | Flight profile | Low-and-slow small-UAS envelope vs. conventional aircraft envelope | 10% |
| Time context | Off-hours | Activity outside normal operating hours scores higher (simple multiplier in v1) | 10% |

Staleness is not a factor (ruled on #6): a track that stops updating is a data-quality signal, not threat evidence, and its treatment is the §5.1 coast window, the drawer's Seen row, and the identity dwell. The weights sum to 95 with the pattern-of-life row (05a).

The UI label column is the spec for what renders in the breakdown bars (Principle 3 — a smart civilian reads it cold); the Intent column becomes the hover text.

Exact curves and weights are decided in PRs 04–05, under unit tests. The table is a starting point, not doctrine.

**As built in 04a** (ruled on #4): each factor contributes its 0–100 value scaled by its weight; the factor lines sum to that weighted total within rounding, and the score is made from the total to one decimal — over the configured weights, then the ceiling — so the printed division reproduces it exactly, as *Score: 69 (caution) — 65.6/95* (the same drone read *82 (warning) — 65.6/80* over 04a's five rows), so the arithmetic travels with the number, lands in the same band, and reads 0–100 whatever rows the table carries. Cooperativity reads the per-frame identity and an **identity memory** of when each ident was last heard — a heard ident holds for a dwell, then degrades linearly toward the Unknown value and stays there; a track never heard scores as silent whatever the generator's label, because the two are observationally the same. Closing is CPA × time-to-CPA on linear roll-offs in ring radii and minutes; proximity is 100 inside the ring, rolling off to nothing at three radii; the kinematic profile is 100 inside the Part 107 box the silhouette already labels, rolling off above it on either reading; off-hours is a step outside the configured operating hours, scored at the scenario's configured clock start, which the strip shows. A track on the ground scores no geometry at all. **The ADS-B ceiling:** after the sum, a track whose observed source is ADS-B is capped at a configured value below the caution band, and the cap prints as its own breakdown line — the §2 guardrail as arithmetic, keyed on source, never on a label. The scorer's input type strips the answer key, so no factor can read it. Every number lives in `src/config/scoring.ts`.

**As built in 05a** (ruled on #5). **Pattern of life** is three detectors over a track's **position history** — where it has been at the frame-grid instants of the last seven minutes, sampled at the clock exactly as the map's trail is, positions and nothing else — and the factor is the strongest of them: **loiter dwell**, the trailing time the track has spent inside one 450 m circle, worth 0 at 150 s and 100 at 300 s, so a 12 kt straight line and a grid sweep's U-turn both read 0; **orbit**, the turn held in one direction for at least 90 s, worth 100 at 270°, and named an orbit only past 180° held — a departure turn is a turn; **area revisit**, back within 400 m of a position left at least 600 m behind two or more minutes ago. A pattern is *named* — loiter and revisit at 50, orbit past the half circle — and the name lives on the score for the reason tag, the record, and the handoff (05b); the breakdown row is labelled for what it measures, **Pattern of life**, and its detail line carries the evidence alone (*within 450 m for 4 min 15 s*), so a real aircraft's breakdown never wears a verdict word. The generator's behavior labels are the answer key the detector tests grade against, never an input. **Inside the ring the approach is complete:** closing reads 100 for any track inside a protected site's ring — the closest approach to the volume is now — where the CPA/TCPA geometry, built for the approach, read whichever way a parked drone happened to point; outside the ring the factor is unchanged. The pattern row scores and prints on a cooperative aircraft too, under the ceiling, which no pattern lifts (4A): on a real aircraft a pattern is ordered within the capped block, not surfaced.

**The friendly launch cap** (08b, ruled on #86), the ceiling's sibling: after the sum, a track whose observed first-seen position lies inside a friendly launch area and which is heard on Remote ID — this frame, or within the identity dwell — is capped at `friendlyCap`, its own configured value (30), below the caution band, and the cap prints as its own line, `Friendly launch — capped at 30 (uncapped 80)`, with the reason tag leading *Friendly launch*. The same mechanics as the ceiling: the capped block orders by uncapped composite, the pattern row still scores and prints, and the never-re-surface guard keys on the condition rather than on the cap having bound. Two observations, no label: a silent track first seen inside the area reads no cap, and the cap lifts when the ident lapses — on 001's intermittent inject the dwell keeps the cap through the ident's gaps where a per-frame read would flicker it 22 times. A real aircraft is never under it; the ceiling is its cap.

### 7.1 Workflow — grounded in the current US domestic framework

Vigil maps onto the detect → track → identify → assess → act chain like this: detection and tracking are the feed layer, identification is the cooperativity layer, assessment is the scoring engine plus a human. The act step is where domestic reality bites: under the SAFER SKIES Act (Dec 2025) and its July 2026 implementing rule, mitigation is reserved for certified personnel operating inside a federal process — credible-threat determination, real-time ATC notification, FBI/DHS notification, proportionality, and mandated reporting. A watch floor's act is therefore a **coordinated notification with the evidence attached**, and Vigil is built for exactly that. The framework runs on notification and reporting, so the defensible record isn't a nice-to-have — it's the feature.

**Track lifecycle** (every transition timestamped to a per-track event log): **New → Assessing → Escalated → Resolved**, plus **Dismissed** for benign tracks. Actions: **Assess** (claim the track), **Escalate** (pick a recipient from a mock contact list — Airport Operations, PHL Tower, Airport Police C-UAS unit — and Vigil generates a handoff summary: track history, score breakdown, event timeline, as copyable text), **Dismiss**, and **Resolve** (with a disposition drawn from the configured list — an outcome label is doctrine, and doctrine is configuration). The table as ruled at the 03b gate: Assess claims a New track; Escalate only from Assessing — a track is claimed before it is handed off; Resolve only from Escalated; Dismiss from New or Assessing; Resolved and Dismissed are terminal for MVP — no reopen. Actually transmitting the handoff is Phase 2; per §2, the act step ends at notification — no simulated engagement.

**The record under the clock** (06b, ruled on #6). Two kinds of entry share a track's log: the operator's actions, which move the status, and observations, which carry it unchanged — first sight, and a **band crossing**: when a track's score changes band in either direction, one entry is logged at sim time (`Warning — up from caution`, in the words of the one band table), on a terminal track too, and it is never a lifecycle change; the band stays a display of the score. Detected against the band the record last saw, so a seek logs at most one crossing. **A pattern's onset and end** are entries of the same kind (05b): `Loitering — began`, `Loitering — ended`, `Orbiting — began, loitering ended`, detected against the pattern the record last saw, forward-only, on terminal tracks too; a track first seen with a pattern already named carries the word on its first-seen entry instead — `New — first seen, loitering` — so a track opened cold and escalated still hands off with it in the timeline, which is where the handoff carries the word. **The handoff's evidence block is frozen at escalation**: Track, Range, kinematics, and Score print from the escalate event's own snapshot — the score rebuilt from the snapshot's factor values and weights, the record's doctrine rather than the live config — and the Range line names the moment (`… at 02:33:00`); the timeline stays live, so a later Resolve appends. The ident prints live (it is the track's name); the identity is the snapshot's.

**Lost and Regained** (#71, ruled; #36 [10], [11]). A track with a non-terminal status that coasts out of the picture logs one line, `Lost — last heard 02:32:00`, at sim time in the same log: an observation, statuses carried, forward-only — rewound to before a track's first sight the picture shows it absent, and the frontier is what keeps that from writing Lost. The record logs what it saw when it saw it, one per seek, at the seek target; the line names the sim time the recording last heard the track, the last message before the loss, so it is true whenever it was stamped and is the fact the next operator needs. Its snapshot is the picture as the operator last saw the track. A terminal track logs nothing: its record is closed. A lost track's frontier is its loss, a moment the track is not in the picture, so the workflow cannot act on it until Regained moves the frontier to a moment it can — what #77 already says; a claimed track that goes dark stays claimed in the record, and closing it out is post-MVP. A lost track heard again logs `Regained` with the return picture, and that pass's crossing and pattern change are read against the record before it, so a band left or a pattern ended across the hole is written down after it rather than absorbed. The Queue row leaves with the track and its tag with it; the drawer's status and the re-surface read are untouched. The handoff timeline carries both lines like every other event.

**Acting behind the record** (#77, ruled). Crossings are forward-only, so re-watching cannot run the record backwards; operator actions are held to the same line. While the clock is behind a track's **frontier** — the sim time of its record's last entry — the four workflow buttons are disabled and the drawer says why, re-enabling at the frontier. The reason is in two parts, because a live region that names the clock re-announces on every scrub step: a **static** `role="status"` line carries the state (`Rewound — the workflow acts at the record's frontier`), so seeking behind the frontier announces once and scrubbing announces nothing further, and the two times (`Clock 02:30:30 · record 02:31:00`) sit beside it, outside the region. The action group is described by both halves, since `disabled` also takes the buttons out of the tab order. The action is not clamped to the frontier from a rewound picture, and not stamped at wall time: the action and the picture it acted on carry one sim time, and only the frontier has both. Copy stays enabled throughout — it stamps nothing.

**Site edits are workflow actions** (08a, ruled on #86). Adding, moving, resizing, renaming, re-tiering, or removing a site re-scores the picture at once against the session's set; a band crossing it causes is logged at sim time like any other, never a lifecycle change, and no per-track line records the edit itself — the crossing is the track's line. Behind the record's frontier — the latest sim time any track's record holds, Lost lines included, or the last site edit's — the editor refuses with the drawer's own two-part reason and re-enables at the frontier, so an edit's crossings always land at or past every track's own. **The snapshot carries the sites** that scored it — id, kind, tier, centre, radius, and the name — by the reasoning that put the weights there (#36 [8]): what the operator saw, so a learner knows which geometry produced the label. The handoff's Range line names the site from the snapshot, so a site removed after the escalation is still named, and one line under the kinematics describes it — `PHL Airfield · protected · tier 1 · 5.0 km` — inside the 26 rem fit at the name cap. The snapshot carries the friendly condition too (08b), so a frozen handoff prints `Friendly launch — capped at 30 (uncapped 80)` where the ceiling's line would print for an aircraft; a friendly area on the record reads `Drone unit pad · friendly · 0.5 km`.

## 8. The learned layer — Phase 3, and why not sooner

The ambition is right: more factors, weights that adapt, and surprising signals bubbling up. The honest sequencing:

- **v1 is transparent rules** because learning needs either labels or a normalcy baseline, and on day one we have neither. Shipping mechanics — the actual point of this project — must not wait on an ML research question.
- **Phase 3a — anomaly factor (unsupervised).** Train a simple anomaly model (e.g., Isolation Forest) on "normal" for this AO — built from the ADS-B recording plus background sim traffic, with hour-of-day as a feature. Its output becomes **one factor in the composite**, with a plain-language explanation of what made the track unusual. This is where time-of-day stops being a hand-set multiplier and becomes learned normalcy — a 3 AM drone is anomalous because 3 AM *is* quiet, not because we said so. It's also the mechanism by which unconsidered factors surface.
- **Phase 3b — the feedback loop.** Assess / Escalate / Dismiss / Resolve are operator labels — escalations especially strong ones. Enough of them enable learned weight adjustment (which factors actually predicted what the operator prioritized). The MVP's job is simply to log these actions in a shape a learner can consume later. Each logged action carries the factor values the operator saw **and the weight set they were scored under**, so an event reconciles with its own composite after doctrine moves: the composite is a label of its time, the factor values are the features, and the stored weights say which picture produced the label — a re-weighted queue is then distinguishable from a scoring bug (#64).
- **Candidate features to explore in 3a**, seeded now so they're not forgotten: broadcast anomalies (position jumps, impossible kinematics — spoofing tells), multi-track coordination (two injects moving in formation), first-seen platform behavior at a site, and approach-angle asymmetries.

## 9. Out of scope — MVP

Live ADS-B polling (Phase 2), backend/API and WebSocket (Phase 2), any ML (Phase 3), CoT/TAK output (Phase 4), persistence, auth, multi-user, mobile layout, alerting/notifications, military identification systems (IFF — a civil watch floor has no interrogator, and it sits deliberately outside this repo's lane), sensor-fusion realism (one clean track per object; no detection modeling). Cut to keep the MVP shippable in ~8 weeks of part-time PRs.

## 10. Phasing

- **Phase 1 (this doc):** frontend stub in `main` — recorded ADS-B replay + synthetic injects, transparent engine, three surfaces.
- **Phase 2:** FastAPI backend owns ingestion and scoring; live ADS-B polling with caching; real-data special-status enrichment — emergency squawk codes and MEDEVAC-type callsigns can elevate real tracks *for assistance and awareness, never as threats*; WebSocket feed; frontend swaps replay for the socket — the "plug the backend into the stub" experience, done personally.
- **Phase 3:** learned layer — anomaly factor (3a), then the operator-feedback loop (3b).

## 12. Process contract — every PR, the same path

1. **AI code review** — automatic on PR open; `@claude` for follow-ups. Both runs have the dependencies installed for them and run the four gates before reviewing; the receipt says whether they ran. The reviewer is not the merge authority and its checks are not the gate — step 2 is.
2. **Automated tests** — CI must be green; red CI is a stop, not a suggestion.
3. **Engineering review** — self-review with the checklist below, on the GitHub diff, not in the editor.
4. **Comments + iteration** — reply to every review comment with a fix or a reasoned "won't fix."
5. **Merge** — squash-merge, delete branch.

**Mechanics:** every PR starts as a GitHub Issue — feature PRs carry a mini-PRD (user story + acceptance criteria), cleanup PRs bundle owner-routed Issues. Branch naming `feat/pr-02-scenario-data`. `CLAUDE.md` carries stack, commands, conventions, and the §2 guardrails so the agent enforces them too.

**Self-review checklist:** read the full diff cold; run the app and exercise the change; check every acceptance criterion of the originating Issue(s); at least one test per behavior change, and a test paired with a fix shown failing on the pre-fix code; no dead code or console noise; README diagram updated if this PR adds or removes a module (a stage on the data path) or an edge, or lands a module the diagram already reserves as dashed.
